# Wedding Planner — First-Time User Onboarding: Critical Review

Scope: not the bento layout (covered in `Documents/design/wedding-planner-bento-ux-review.md`) and not the tab-split redesign (covered in `Documents/design/wedding-planner-menu-split-critical-review.md`). This document is about the **onboarding funnel specifically** — how a brand-new user goes from "I just heard OmnyID can plan my wedding" to "the master agent is actively working on my wedding with my email, calendar, and an LLM connected" — evaluated against what a first-time, possibly non-technical, possibly emotionally-invested (this is their wedding) user actually experiences. Review only — no code was changed.

This review also draws on two existing docs in this same folder — `ONBOARDING_API_KEYS_FINDINGS.md` and `ONBOARDING_IMPLEMENTATION_SUMMARY.md` — which already diagnosed and partly fixed the **generic** app onboarding problem. The core finding of this document is that the wedding template does not inherit any of that fix.

## 1. The first-time user's actual path today

Traced directly from the code (`solid-ui/src/lib/weddingTemplateEntryState.ts`, `solid-ui/src/components/ResponseQueueView.tsx`, `WeddingApprovalPreviewPanel.tsx`, `WorkspaceSetupBanner.tsx`, `GuidedTour.tsx`):

1. **Generic account setup** — a new user already passes through up to three stacked, sequential surfaces before touching anything wedding-related: `FirstRunExperience` (Gmail-only tour), `WelcomeScreen` (goals/tone), `OnboardingWizard` (personality/tone/goals/rules). None of these mention weddings, LLM keys, or calendars in any integrated way (per `ONBOARDING_API_KEYS_FINDINGS.md`, section 2).
2. **Discovering the wedding planner at all** — there is no visible "Plan a wedding" entry point anywhere in the UI. `buildWeddingTemplateEntryState()`'s `starterPrompts` (`"Find venues"`, `"Build budget"`, etc.) are only ever rendered *after* a wedding workspace already exists (`ResponseQueueView.tsx`, inside the `weddingTemplateLaunch()` block) — they are not surfaced as suggestion chips on the blank Chat/Home screen before that. The only way in is for the user to already think to type something wedding-related to the chat assistant, or arrive via a marketing-site handoff. **A first-time user who doesn't already know this feature exists has no on-screen invitation to try it.**
3. **The intake form** — once wedding intent is detected, the "Wedding template launch" section (`ResponseQueueView.tsx:979-1240`) renders as a single, un-paginated block containing: a free-text paste box, five separate date/location/guest/budget/priority inputs, a multi-select vendor-type checklist grid, a whole secondary "vow preparation" sub-section (vow choice, vow style, two more textareas), NOIM status, celebrant path, and finally a submit button. **That is 12+ distinct inputs on one screen**, with no step count, no progress bar, and no visual distinction between "answer this now" and "safe to skip" beyond each select quietly defaulting to "Ask later"/"Decide later."
4. **Wedding-content setup checklist** — a smaller, better-designed "Start here" card (`ResponseQueueView.tsx:928-962`) tracks four items: date, budget, guests, helpers. This one is genuinely good — clear labels, one-line consequence per item ("Unlocks RSVPs, meals, and seating"), a live "N to add" counter, done/add states. **But it only covers wedding content. It says nothing about Gmail, Calendar, or the LLM key** — so a user can fully "finish" this checklist and still have zero working connections.
5. **Hitting the connection wall mid-task** — the actual prompt to connect Gmail or Calendar doesn't appear until the user tries to *act* on a planning artifact — e.g. approving a vendor email draft — deep inside `WeddingApprovalPreviewPanel.tsx`. The blocking state's own label is `"Connect provider first"` (`weddingApprovalState.ts` block-kind copy) — generic, uses the word "provider" (a system term, not something a couple planning a wedding would recognize), and gives no wedding-specific reason ("so OmnyID can email this to the venue for you"). Clicking through calls `onProviderSetup` → `props.onNavigate(view)`, which is a bare view switch with **no parameter carrying "return to your wedding when done."** The user lands in a generic settings screen with no visible thread back to the task they were just doing.
6. **LLM API key** — configured entirely inside `AgentSettingsView`'s "LLM & APIs" tab (per `ONBOARDING_IMPLEMENTATION_SUMMARY.md`), a surface with zero wedding framing. Nothing inside the wedding workspace tells a first-time user whether the agent doing their wedding planning even has a working model connected until something silently fails or degrades.
7. **The fix that already exists, but isn't used here** — `WorkspaceSetupBanner.tsx` is a well-designed, already-built component: a collapsible banner with live completion checks for LLM, Gmail, MCP tools, and Skills, each item clickable straight to the right settings view, auto-hiding once complete. It is used in exactly one place: `DashboardFeed.tsx` (the general home feed). **It is never rendered inside `ResponseQueueView.tsx` or anywhere in the wedding workspace** (confirmed by grep — zero references). A user who enters their wedding via chat and lands directly in the Response Queue view may never see this banner at all.

## 2. Critical failure points, mapped to what you asked for

### 2.1 "Guide the user through the interface" — fails on discoverability and on hand-off
There is no invitation to start, and once started, the moment the flow needs something outside the wedding workspace (a Gmail connection), the user is dropped into unrelated app chrome with no breadcrumb back. **Nielsen's first usability heuristic, visibility of system status, is violated twice over**: the user doesn't know the feature exists before they start, and once mid-flow, they don't know where "back to my wedding" is after a detour.

### 2.2 "Ask the user questions to understand the wedding context" — fails Hick's Law and the progressive-disclosure principle
Twelve-plus fields on one screen is the textbook case Hick's Law predicts will slow and discourage completion (decision time rises with the number of simultaneous choices) — and it directly contradicts the **progressive disclosure** principle already correctly applied four items away, in the smaller "Start here" checklist. The product knows how to ask for one thing at a time (the checklist proves it); the intake form doesn't do it. This is an internal inconsistency, not a missing capability — **Nielsen's heuristic #4, consistency**, is violated against the product's own better pattern.

### 2.3 "Connect to Gmail and Google Calendar" — fails contextual-permission-request best practice
Modern platform guidance (Apple HIG, Material Design) and well-known product examples (Superhuman's famously white-glove, single-purpose onboarding; Notion's and Linear's "connect when you need it, with a stated reason" pattern) converge on the same rule: ask for a connection **at the moment its value is obvious**, with a one-line reason in the user's own terms, and **never lose the user's place** doing it. Today: the reason given is "Connect provider first" (a system-status label, not a benefit), and the mechanism (a bare view-navigation call) structurally cannot preserve "return to what I was doing" because the function signature carries no such parameter.

### 2.4 "Connect LLM API key" — fails visibility of system status, specifically inside the wedding context
A first-time user has no way to tell, from inside the wedding workspace, whether the agent that's supposedly "planning their wedding" is actually running on a configured model. The generic `WorkspaceSetupBanner` already solves exactly this (a live, clickable, auto-hiding completion check) — it's simply not present here.

### 2.5 "Use master agent to plan out the wedding" — fails the "aha moment" / time-to-value principle
`canStartUnder60Seconds: true` in `weddingTemplateEntryState.ts` shows real intent to deliver a fast first win — this is the right instinct (it's the same instinct behind Superhuman's and Slack's celebrated onboarding case studies: get the user to a genuine payoff fast). But the payoff is currently gated behind discovering the feature exists, then a 12-field form, before the agent produces anything. **The Peak-End Rule** (Kahneman) says people judge an experience heavily by its most intense point and its ending — right now the most intense point of a first-time user's wedding-planning onboarding is a long, undifferentiated form, not a moment of the agent doing something delightful.

### 2.6 Responsiveness and "loud and clear next step" — partially solved, inconsistently applied
The tab bar, cards, and the "Start here" checklist all use sensible responsive classes (`sm:`/`md:`/`xl:` breakpoints, a `compactMode()` signal already threaded through). But the giant intake form uses `md:grid-cols-3` for many of its fields — on a phone, that's 12+ stacked full-width inputs in a row, a much longer scroll than the same information would need as a proper stepped flow. And "loud and clear next step" is currently **contested by four competing surfaces that can all be relevant at once**: `WeddingNavigationArrivalBanner`, `WeddingPlannerWalkthrough`, the "Start here" checklist, and the "Wedding template launch" form. Nothing establishes which one wins if more than one condition is true — the opposite of a single, unambiguous next action.

## 3. What "award-winning" onboarding would actually do differently here

Concretely, not just in principle:

1. **One unmistakable entry point.** Put a wedding-planning suggestion (one of the six `starterPrompts` already written, e.g. "Find venues") as a visible suggestion chip on the blank Chat/Home screen — not only after the workspace already exists. This is the same move Notion, Linear, and ChatGPT itself make on a fresh session: show a few concrete example prompts so a new user doesn't have to guess what's possible.
2. **Replace the 12-field mega-form with a single-question-at-a-time flow**, the pattern Typeform made famous and that directly follows from Hick's Law: one field or tightly-related pair per screen, a visible step counter ("3 of 7"), a persistent "Skip — decide later" that's exactly as visually prominent as "Next," and the free-text paste-a-message box offered *first*, as an alternative to the whole flow, not buried as one option among many (if the user pastes a message with enough detail, skip straight to a summary-and-confirm step instead of asking the other 11 questions at all — this is what the extraction logic already technically supports, it's just not the visual hierarchy the form conveys).
3. **Merge the wedding-content checklist and the connections checklist into one visible progress surface**, reusing `WorkspaceSetupBanner`'s already-built pattern (live checks, clickable items, auto-hide on completion) rather than the wedding template's own narrower four-item version. One list: date, budget, guests, helpers, Gmail, Calendar, LLM model — all in the same place, all with the same visual treatment, so "what's left before this actually works" is a single glance, not a scavenger hunt across two different checklists that don't know about each other.
4. **Never navigate away to connect something — do it in place.** `BentoGrid.tsx` already imports Solid's `Portal` elsewhere in this codebase; the same mechanism can render Gmail/Calendar connect as a modal *over* the wedding workspace rather than a full view switch, so there is no "lost my place" moment at all. If a full navigation is unavoidable for some providers, at minimum pass a return target through `onProviderSetup` so the destination view can render a "back to your wedding" affordance — right now the function signature (`(view: ViewName) => void`) structurally cannot carry that information.
5. **Reframe every connection ask in wedding terms, not system terms.** "Connect provider first" → "Connect Gmail so OmnyID can send this to the venue for you." "Open setup" → tie the copy to the actual artifact waiting on it. This is a copy-only change with outsized impact — it's the difference between a system reporting its own internal state and a product explaining what's in it for the user.
6. **Make the agent's first real output the peak, not the form.** Given `canStartUnder60Seconds` is already a stated goal, consider whether the very first screen should be closer to: paste-a-message-or-answer-three-things → agent immediately produces one real artifact (e.g., a venue shortlist draft, even a rough one) → *then* offer the deeper intake (vow preparation, NOIM, celebrant path) as follow-up, once the user has already seen value. Right now all the depth is front-loaded before any payoff.
7. **Pick one arbiter for "what to show next" among the four competing surfaces.** A simple priority order (e.g., arrival banner only if no workspace yet → walkthrough only on first visit to an existing workspace → unified setup checklist thereafter until complete → nothing once done) would turn four possible simultaneous prompts into one deterministic one, which is the entire point of "loud and clear."

## 4. Suggested phasing

1. **Cheapest, highest-leverage first**: reword the connection-blocking copy in wedding terms, and add the missing "return to your wedding" affordance to the provider-setup navigation. Pure copy + one extra parameter.
2. **Reuse, don't reinvent**: render `WorkspaceSetupBanner` (or a wedding-aware variant of it) inside the wedding workspace, merged with the existing four-item wedding checklist, instead of maintaining two separate, incomplete lists.
3. **Discoverability**: surface a wedding starter prompt on the blank Chat/Home screen.
4. **The bigger lift**: break the 12-field intake form into a stepped, skippable, progress-visible flow, with the free-text paste option promoted to the first and most prominent choice.
5. **Sequencing**: establish the single priority order across arrival banner / walkthrough / checklist so only one "what's next" signal is ever shown at a time.
