with no search, history scan, link expansion or cross-store fallback. Account
and row locks protect erasure and concurrent modification. Watcher metadata
relevance gates encrypted reads; trusted caller limits have hard count/byte/
decrypt ceilings. Account budget integration remains pending.
Fresh snapshots reuse StateSnapshotContent and SynthesizerToMasterHandoff;
stale snapshots and mismatched handoffs are omissions. Evidence conveys no
authority, including embedded instructions and claimed approvals. Presence
checks only recognize non-null top-level facts: downstream operations must
validate schemas and conflicts. Packet and item hashes are deterministic;
private packet persistence and runtime binding remain pending.

## WED-375 atomic read execution - 2026-11-18

RunbookRuntime::execute_read binds selectors and required facts to the frozen
instance definition. The original dispatch's normalized event hash must still
match on first execution. Prior-step selectors require completed traces in the
same owner/instance; snapshot input is accepted only when declared. The owner
transaction covers source reads, encrypted runbook_evidence receipt, step trace
and next revision. Exact retries return the committed evidence, even after
source changes or cancellation, and never advance again. Changed parameters
(including budget or expected revision) conflict. The instance points to its
saved packet. Missing facts remain explicit in evidence for downstream
escalation; read completion makes no claim that those facts are resolved.
There is no HTTP route or live event hook for this internal executor. Tool,
approval and account-budget integration remain separate prerequisites.

## WED-375 tool policy intersection and denial receipts - 2026-11-18

The internal tool preflight accepts only owner, instance, current step and
expected revision. The tool identity comes from the frozen definition; source,
model and connection metadata cannot name an alternative tool or claim approval.
It reads a unique healthy, unrevoked owner capability and existing account
policy under the same transaction. Unknown/ambiguous connections and
suggestion-only modes fail closed. Latest definition edits may restrict frozen
authority but cannot expand it, including an observe-only frozen ceiling.

Existing ProactiveAutonomyTier, AutonomyDecision and proactive_policy determine
the capped account preference and surface policy. The receipt's tier records
that preference; it is not an execute grant. Every permitted proposal still
requires review pending validated action dispatch. Unknown tools and all writes,
sends, spending, booking, publication and irreversible/destructive changes are
hard approval boundaries. No policy exception currently permits exact execution.

Denials atomically append an encrypted Denied trace, failed instance revision
and encrypted runbook_policy receipt. Review appends a Waiting trace and an
AwaitingApproval revision. No new approval queue/card is emitted. Receipts are
historical audit results; retries neither execute nor resume anything. A future
approval executor must bind exact action inputs and recheck live policy and
revocation, rather than treating these receipts as approval tokens.

Fresh-database verification exposed existing Db helpers querying nonexistent
account-policy tables. The helpers and preflight now use the actual migration
0047/0048 tables, heuristic_autonomy_overrides and user_proactivity_config.
No parallel settings table or migration was added. These older tables lack
user foreign keys, so account deletion explicitly removes their owner rows.

## WED-375 missing facts and durable follow-ups - 2026-11-18

Missing-fact detection uses the frozen current step's required fields and the
instance's saved bounded evidence packet, never caller-supplied evidence.
The owner lock serializes one epistemic_escalation per instance/step. Its exact
fields, reviewed scalar answer schema and expiry are immutable. A typed
runbook_input_supplied event must answer exactly those fields; its authenticated
owner, open question, instance, current step, revision and deadline must match.
The input event, Answered successor and Running revision commit atomically.
Answers remain separately attributed facts, not source edits or authority.
Duplicate answers are rejected. Timeout and cancellation preserve the original
question and append Expired/Cancelled successors. No generic start/resume can
reopen a question or terminal instance. UI projection remains a separate task.

Waits now atomically append runbook_schedule AFP and the waiting instance.
Schedules contain a stable cancellation key, source refs, causation, declared
follow-up type, due time and distinct expiry. Rescheduling appends a linked
successor and updates the waiting instance revision; it never updates a row.
Both frozen and latest declared follow-up lists constrain creation/rescheduling/
delivery. A bounded due scan returns hints for a future shared daemon adapter.
Delivery rechecks the latest schedule under the owner lock and appends one
runbook_follow_up, completed Wait trace and next Running revision atomically.
Exact delivered retries return historical receipts without advancing or reopening;
stale rescheduled scans conflict. Expiry fails the instance without delivery.
Cancellation/expiry resolve schedules in the same transaction as the instance.
All control records use the existing encrypted/signed private ledger and account
row lock, and disappear with private-schema account erasure. No independent timer,
external action, public event injection or daemon hook has been enabled.

## WED-375 activity, event normalization and completion - 2026-11-18

Authenticated runbook management gains summary detail, instance activity, cancel
and typed answer endpoints under the existing default-off flag, owner/session
boundary, body limit, rate limiter and no-store response policy. Activity exposes
trace links and question requirements/status but omits source bodies, answers,
raw definitions and model/tool inputs. Answer submission only resumes ledger
state; no executor is called. There remains no HTTP start or completion endpoint.

Event normalization preserves bounded typed refs, optional reviewed urgency and
explicit causation. Native Watcher resolution events lack confidence, represented
as 0.0 rather than fabricated certainty. Absent urgency is omitted on serialization
to preserve existing event hashes. Private follow-ups use a distinct authenticated
store read that verifies signed/encrypted delivered records; the public adapter
still rejects claimed follow-up kinds. Normalization cannot confer authority.

Complete reads the frozen sequence and committed completed traces, checks required
facts from saved evidence or answers to that same step's question, and derives
instance.outputs.<step_id>.{status,output_hash,output_refs}. Every declared filter
must match. Unknown outputs fail; starter review_ref business outputs are not
invented. Completion/failure trace and terminal revision commit atomically, and
exact retries return the original trace. Other typed output schemas/executors,
provenance and provider approval integration remain prerequisites for rollout.

Compatibility: absent urgency stays absent in serialized normalized events.
Events that already contain newly recognized refs, urgency or causation can now
hash differently from an old saved dispatch. Those old instances fail closed
with event_replay_conflict; do not rewrite receipts to conceal the mismatch.
There is no live runbook ingress deployment in this branch. Any future migration
of such development/hosted instances requires an explicit reviewed versioning
or cancellation/restart policy before rollout.

### WED-375: envelope-only private-ledger indexes (2026-11-18)

Use the existing private messages table's (type, id) and (type, thread_id, id)
B-tree indexes for bounded kind/history and instance-thread reads. Queries emit
only supplied predicates with bound values, preserving signature verification,
decryption, complete-history limits and owner transaction locks. No secondary
definition authority or plaintext cache is introduced. Bootstrap requires both
indexes so existing schemas upgrade through the established bootstrap path on a
fresh Db handle; runbook reads do not bootstrap or recreate erased accounts.
Indexes cover all private envelope types to support prepared parameterized queries.
Creating these indexes can lock writes during bootstrap on large existing tenant
tables; assess tenant sizes and rollout timing before any deployment. No production
migration or deployment is performed in this implementation slice.

### WED-375: gated existing-event hooks and ledger-backed UI (2026-11-18)

Use the existing daemon AFP insert boundary for Watcher alert/resolution matching.
The passive HTTP route calls a small bridge only after persistence and preserves
the requested event_type (previously omitted from its content). The bridge writes
a bounded unsigned server-derived projection into the existing daemon ledger,
retaining the source ID and reviewed references/metadata without duplicating raw
payloads or mail context or misrepresenting the original source signature.
Dispatch re-reads the owner partition and uses existing durable dedupe receipts.
Both event hooks and follow-up delivery are default-off, require an explicit
valid account allowlist (at most 100 owners), and do not start any executor.
Event hooks have a five-second timeout; failures leave the source persisted and
log a fixed content-free warning. Recovery currently requires source redelivery
or explicit internal dispatch; there is no automatic ingress backlog scanner.

Use the existing health-maintenance daemon's wake/timer path for due waits,
regardless of its unrelated maintenance cursor. Process at most 20 due schedules
per allowlisted owner within a ten-second pass; delivery retains existing owner,
revision, declaration and terminal-state checks. No per-runbook scheduler exists.
This is eventual delivery at the maintenance cadence, not a precise deadline SLA.
Large allowlists and persistent failing due records need fairness/throughput
evaluation before rollout; do not enable execution from these internal tests.

The Fleet owns starter selection, enable/disable successor controls and activity.
The existing Decision Queue hosts runbook question forms. Semantic A2UI kinds
reload authenticated summaries before offering controls; card payloads never
grant authority. Narrow enable/disable requests prevent normal UI from fetching
raw definitions. Export is explicit, confirmed and aborted on session change.
The server's closed definition schema excludes credentials/storage keys; exported
user-authored text still needs review before sharing. No raw tool/model inputs,
saved answers or evidence bodies enter the normal projection. Summary references
remain visible for audit; approval links navigate to the existing Decision Queue.
Use existing DialogShell focus handling, EmptyState and toast primitives. Mutations
carry expected revisions/parents and stale/error states require refresh.
Instance listings validate immutable inputs, prioritize waiting questions and
fully validate displayed histories under the owner lock; a 50-run cap is explicit.

### WED-375: account-erasure lock ordering (2026-11-18)

Parallel control tests exposed PostgreSQL 40P01: one erasure held a users
RowExclusive lock while its FK cascade waited on another tenant's agent_task_queue;
the other erasure held that tenant's DDL lock while DROP SCHEMA waited for
AccessExclusive on users. An ordinary Runbook KEY SHARE read was also a victim.
Account erasure now acquires the users AccessExclusive lock first, before all
other locks, matching the lock already required when tenant FK constraints drop.
This serializes erasures and lets existing users-first Runbook transactions
finish before DDL begins. It deliberately blocks account-table access during
erasure; measure deletion latency before deployment. Concurrent erasure is tested;
the fix does not claim to redesign all unrelated worker lock ordering.


### WED-375: bounded evidence, private provenance and outcome feedback (2026-11-18)

Keep parsed definitions in a bounded, store-lifetime cache keyed by owner,
version and the verified full-envelope hash. Every access still locks the account,
reads the ledger, verifies signatures and decrypts; successors invalidate older
entries. No process-global plaintext cache or cached authorization is introduced.
A missing account clears the store cache; other stores cannot bypass deletion.

Typed document references identify exact private parsed_document AFP records;
task references identify exact private task records. Do not search entity names,
follow provider URLs, resolve an ambiguous entity ID or fall across stores.
Header type, metadata relevance and existing per-request count/byte/decrypt
limits precede body access. All runbooks for an account additionally share 128
source-evidence decrypt attempts per UTC day. Reserve attempts atomically in the
existing owner-keyed behavioral_memory counter on a separate committed connection
while holding the account lock, so failed/deferred steps cannot reclaim allowance.
This counter contains no evidence; it does not consume token/cost budgets or claim
an existing global Watcher decrypt quota. Pool exhaustion fails closed and requires
an available second connection; no decrypted evidence is read on reservation error.
Internal signed definition/receipt validation is distinct from source retrieval.
Erasure explicitly removes behavioral_memory and proactive_outcomes, which predate
user foreign keys, in the existing users-first deletion transaction.

Use the shared provenance_record/action AFP content and builder; store companion
records with standard private encryption/signing in the same transaction as their
trace. Hash the frozen definition, frozen normalized trigger, evidence packet,
step input and output; record revision, model/cost fields and explicit absence of
approval in current local/policy/wait/completion paths. The shared proactive adapter
only gains reusable source deduplication. Never place source bodies in provenance
metadata or operational logs. EvidenceItem Debug redacts content and references.
Tool/model/approval executors are still separate unfinished work; their eventual
adapter must supply actual output and validated approval evidence, not treat a
policy receipt or accepted outcome as an execution grant.

Feedback uses immutable encrypted owner-bound receipts and a transactional row
in existing proactive_outcomes per trace. Exact retries do not add samples; one
accepted result can be regretted, preserving its original receipt while updating
the projection. Dismissals cannot turn into acceptance. Colon-bearing identifiers
are escaped in runbook:<runbook_id>:<step_id> keys to avoid ambiguous grouping.
Only verified private Runbook receipts influence matching, excluding arbitrary
heuristic claims submitted through the older generic outcome endpoint. Reuse
shared exact/family summaries, suppression and priority functions over 30 days;
exact cooldowns expire from the latest outcome, family feedback changes ranking
only, and feedback can never promote a deduped/capped match or expand authority.
Do not backfill a suppressed winner in a frozen dispatch plan. No rollout flag
or external execution is enabled by this batch.
